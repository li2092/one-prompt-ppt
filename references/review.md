# 独立评审：以听众的身份读一遍

大纲的整体检查通过后做这一步。脚本只查形状；内容是否讲得通、听众是否听得懂，要由没参与制作的人来读。

## 一、谁来评审

评审者不能看到制作过程，只拿到两样东西：`大纲.md`，以及本文件第二节的评审要求。

- 运行环境能派子 agent 时，派一个新的子 agent 来评审。评审用的模型不必比制作用的更强。
- 不能派子 agent 时，自己评审：先把制作时的思路放下，从头读 `大纲.md`，只根据纸面上写的内容判断。

不把原始材料、制作中的讨论、自己的解释给评审者。听众到时候也看不到这些。

## 二、给评审者的要求

把下面这段原样交给评审者，并附上 `大纲.md` 的路径。

```text
你是这份汇报的听众。你的身份、背景、最在意的事写在大纲开头的“听众与定义卡”里，
请完全按那个身份来读，不要用你自己的专业知识补全。

请读完整份大纲，然后回答下面的问题。每个问题都要指出具体的页码或章号，并引用原文。
没有发现问题就写“没有”，不要为了凑数而挑毛病。

第 0 层 听众
1. 哪些词、缩写或说法你（作为这位听众）看不懂，或者需要停下来想？
2. 哪些内容是你早就知道的，讲了是浪费时间？
3. 你最在意的那几件事，各在哪一页得到了回答？有没有哪一件没有回答？

第 1 层 整份
4. 只读主旨句和各章论点，你会被说服吗？哪一步你会问“凭什么”？
5. 各章之间有没有接不上的地方？

第 2 层 章
6. 哪一章读完后你说不出它的结论？
7. 哪一页放在这一章里显得多余，或者哪里缺了一页？

第 3 层 页
8. 哪一页你看完标题和导语，仍然不知道它想说什么？
9. 哪一页的结论条只是把标题重复了一遍？

第 4 层 块
10. 哪个图示所标的关系和它的内容对不上？例如标的是先后步骤，内容其实没有先后。
11. 哪一处的结论没有依据，或者依据和结论对不上？

最后
12. 如果只能改三处，你会改哪三处？按重要程度排列。

只提问题和理由，不要改写大纲。
```

## 三、怎么用评审意见

1. 逐条判断是否成立。评审者可能误读，也可能说得对。
2. 成立的意见按层归位，从上层改起。听众层和整份层的意见会牵动论证树；论证树已经由用户确认过的，改动要在交付时告诉用户。
3. 不成立的意见写明理由，一并交给用户。
4. 改完重跑整体检查。评审做一轮即可；改动很大时再做一轮，最多两轮。两轮之后仍有的意见写进交付说明，由用户判断。

交付时把评审提出的问题、改了哪些、没改哪些及理由，都写给用户。
